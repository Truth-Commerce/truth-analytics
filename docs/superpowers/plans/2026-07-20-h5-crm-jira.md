# H5 — CRM estilo Jira Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** O plano de ação vira um CRM estilo Jira: hierarquia épico→task→subtask com progresso agregado, ticket completo (labels, watchers, menções, markdown, links), board turbinado (filtros, drag-and-drop real, edição inline, swimlanes, badge de SLA), e ciclos/sprints com burndown e retrospectiva de impacto em venda.

**Architecture:** Estende o CRM da F2/G3 sem reescrevê-lo. Uma tabela `tasks` (não uma nova de épicos): `parent_id` (auto-FK) + `nivel` (`epico|task|subtask`, 3 níveis fixos) + `labels` (jsonb) + `cycle_id`. Novas tabelas org-FK: `task_watchers`, `cycles`. Toda lógica de decisão (progresso do épico, validação de hierarquia, filtros do board, swimlanes, SLA, burndown, retrospectiva) mora em módulos PUROS testáveis; repositórios só fazem I/O org-scoped; ações usam os requires já endurecidos pela H4 (`requireActiveOrgParaMutacao`/`assertNaoImpersonando` — o CRM já está sob impersonation read-only). DnD real com pointer events nativos (mantém a decisão F2 de zero lib nova; fallback `@dnd-kit` só se inviável).

**Tech Stack:** Next.js 14 (RSC + client components para o board interativo), Drizzle+Neon, Vitest. Sem lib nova (a menos que o fallback DnD seja necessário — decisão no plano da task).

**Branch:** `feat/h5-crm-jira` (base: `master`).

**Decisões de plano:**
- Hierarquia numa tabela só (`parent_id`+`nivel`), 3 níveis fixos; subtask herda `org_id`/`report_id` do pai; épico agrega progresso das filhas diretas.
- `task_watchers` e `cycles` têm org-FK → ENTRAM no purge NA MESMA task do schema (lição institucionalizada H1/H2/H3).
- Board interativo (filtros/DnD/inline/swimlanes) é client component; lógica pura em view-models `.ts` (vitest node), o client só orquestra.
- Menções `@usuário` disparam notificação in-app via `notify()` existente; watchers idem.
- SLA reusa `src/modules/tasks/sla.ts` (já existe: `statusPrazo`, `SLA_DIAS`, `labelPrazo`).
- Ciclos: burndown = tasks abertas por dia (puro); retrospectiva = concluídas vs planejadas + impacto em venda reusando o motor de impacto da F2 (`task-impact.ts`/`impacto-renovacao.ts`).
- Impersonation: NENHUMA ação nova de mutação do cliente pode escapar do read-only — toda action nova segue o padrão H4 (guard como 1ª linha).

## Global Constraints

- **Migration 0016 ADITIVA e OBRIGATÓRIA antes do deploy:** `tasks.parent_id`/`nivel`/`labels`/`cycle_id` (colunas nullable/default — retrocompat: tasks existentes viram `nivel='task'`, `parent_id=null`, `labels=[]`), `task_watchers`, `cycles`. CHECK de `nivel`.
- **Retrocompat do CRM existente:** o kanban atual e todas as tasks da F2/G3 continuam funcionando idênticos (tasks sem épico/ciclo = comportamento de hoje). Testids/textos/E2E existentes preservados (E2E do kanban é guard).
- **Multi-tenancy:** toda query nova filtra `org_id`; toda ação nova de mutação do cliente usa `requireActiveOrgParaMutacao` ou roteia por `resolveTaskContext` (já guardado por `assertNaoImpersonando`); ações do analista via `assertOrgAccess`.
- **Sem lib nova** (exceto fallback DnD decidido no plano da task). Novos testids com prefixo `crm-`.
- Testes: unit puros + integração `describe.skipIf(!url)` PREFIX+RUN cleanup escopado.
- NOTA ambiental (dono ainda vai consertar): relógio Windows +3h + DB test sujo derrubam ~13 suites (rate-limit×2, watchdog, purge-org, cron-*) — se forem as ÚNICAS falhas, reportar pré-existentes; NÃO deixar testes NOVOS dependerem do relógio da máquina.
- Comandos: `npm run typecheck` · `npm run lint` · `npm test` · `npm run build` · `npm run test:e2e` · `npm run db:generate` · `npm run db:migrate:test`.
